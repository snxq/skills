# my-feature-dev

功能迭代多任务开发的编排流程：阶段规划 → 公共依赖先行 → 子 Agent 并行开发（worktree）→ 测试（纯本地运行 + 外部依赖 mock）→ 子 Agent 审查 → MR 管理。主会话是组织者与上下文管理者，不直接写业务代码。

## 何时使用

一个迭代/版本内有多个后端开发任务（数据层、任务改造、多个接口），需要有序并行推进并各自评审、MR 由人工合入时。

## 核心约定

1. **基于 origin 的迭代基线分支为起点**：任务分支以 `origin/<迭代基线分支>`（已含先行件）为起点，不基于本地特性分支，避免 MR diff 携带无关提交。
2. **用 worktree 创建分支**：每任务独立 `.worktrees/<分支名>`，并行互不干扰。
3. **尽量用子 Agent 执行具体工作**：建 worktree、开发、测试、提交、建 MR（只创建，不合并）均由子 Agent 执行。
4. **尽可能并行子 Agent**：无依赖任务同一批派发；每个子 Agent 独立 worktree、零文件重叠。
5. **主会话负责组织与上下文管理**：阶段规划、任务书编写（基线、目录、MR 目标都写清楚）、对审查结论裁决；**对子 Agent 产出的审查另起子 Agent 执行**，主会话不自己读码。
6. **绝不合并 MR**：所有 MR 的合入一律由人工执行；主会话与子 Agent 只负责创建 MR、验证 MR，收到"帮我合并"类请求时拒绝并说明。
7. **测试纯本地运行、外部依赖一律 mock**：测试环节不连接任何外部/共享环境（远程 DB、Redis、外部 HTTP 接口、消息队列等），外部依赖必须通过接口注入，测试时替换为 mock 实现；注入边界在开发阶段就要建立，存量无边界代码在先行件中改造。

## 输入文档依赖（开工前收集齐全）

| 文档 | 用途 |
| --- | --- |
| 需求规格（PRD） | 业务口径、判定规则、验收标准 |
| 需求原型 | 页面交互、数据范围、字段语义 |
| 后端技术方案 | 数据层设计、接口设计、计算任务设计 |
| 前端接口对接文档 | 前后端契约：请求/响应字段、枚举、异常返回的**权威定义** |
| 后端工作内容 | 工作项清单、依赖、交付物 |

**权威优先级（字段/口径冲突时）**：前端接口对接文档 > 后端技术方案 > 需求规格/工作内容。文档自身标注差异处以前端文档为准，并在 MR 描述注明。

## 流程

### 1. 阶段规划（由具体项目分析，非模板）

- 画工作项依赖图：编号 → 依赖 → 人日 → 交付物。
- 区分三类：
  - **先行件**：所有下游依赖的公共层变更（数据模型/常量/公共枚举等），必须最先完成并由人工合入基线。是否涉及数据层由项目实际情况决定。
  - **关键路径**：被最多下游依赖的任务。
  - **独立件**：只依赖先行件、可并行。
- 阻塞项（外部接口字段、调度参数确认等）单独列清单，标注关闭时机。
- 识别各任务的**外部依赖清单**（数据库、缓存、外部 HTTP 接口、消息队列、定时调度等），逐项确定 mock 方案与注入边界；无注入边界的存量代码列入先行件改造范围。
- 文档先行（L0 类）：接口对接文档 Day1 输出，前端可 mock 并行，不阻塞后端。

### 2. 先行件落地

- 公共层变更先行完成：与设计文档逐项核对产出；需运营可调的值做成「默认值 + 配置项 + 按次读取」；既有公共资产复用不重定义。
- 先行件独立 MR，先行 review；合入迭代基线分支由人工执行（Agent 不合并）。

### 3. 并行任务开发（子 Agent 执行）

主会话为每个任务编写任务书，**在上下文中描述清楚，由子 Agent 自行执行建 worktree、开发、提交、建 MR**。任务书必备：

- 任务目标、范围与明确不做项；
- 参考文档路径 + 相关章节（注明权威优先级）；
- **基线**：`origin/<迭代基线分支>`；**worktree 目录**：`.worktrees/<分支名>`；**分支名**；
- 先行件资产清单（DAO、常量、配置读取方式等已就绪的依赖）；
- 校验约定（编译 + lint 全量、区分新增/既存问题；开发期不跑全量测试，全量测试在测试环节执行）；
- **测试约定**：测试纯本地运行——外部依赖一律 mock（HTTP 用本地 mock server/httptest，DB 用内存实现或 sqlmock，缓存用内存实现，MQ 用 mock producer/consumer），禁止连接任何外部/共享环境；测试配置使用本地 mock 配置，不得出现真实环境地址或凭据；
- 提交约定（提交信息规范）；**MR 约定**（目标分支、标题格式、描述要素：依据文档/变更内容/验证/确认点）。

任务间文件零重叠。

### 4. 测试（纯本地运行 + 外部依赖 mock，子 Agent 执行）

每个任务开发完成后、提交/建 MR 之前，由开发子 Agent 在本任务 worktree 内执行测试验证，通过后再交付审查：

- **纯本地运行**：测试不依赖任何外部网络、共享环境或真实凭据，单机即可完整通过（如 `go test ./...`）。
- **外部依赖一律 mock**：
  - 外部 HTTP 接口：本地 mock server（如 `httptest`），按前端接口对接文档的响应样例构造返回；
  - 数据库：内存实现（如 sqlite `:memory:`）或 `sqlmock`；本地容器默认不引入，仅在任务书明确标注需验证 SQL 方言语义且主会话批准时可选；
  - 缓存：内存实现（如 `miniredis`）或注入的 mock 客户端；
  - 消息队列/定时调度：mock producer/consumer，不得触发真实发送。
- **注入边界**：外部依赖必须经接口/依赖注入接入，测试时替换 mock 实现；无边界的存量代码先在先行件改造，不得以"连真实环境"绕过。
- **测试范围**：新增与修改路径必须有单测覆盖（至少正常路径与核心异常分支，其余边界/异常分支按任务书标注的重点覆盖）；冒烟验证以本地 mock 配置启动服务并实际调用一次新接口，无新接口的任务改为以本地 mock 配置启动服务后执行一次任务逻辑并验证结果。
- **禁止事项**：测试代码或配置中出现真实环境地址与凭据；测试依赖执行顺序或共享外部状态。

### 5. 审查（另起子 Agent）

- 每个开发子 Agent 完成后，**另起审查子 Agent**：提供任务书、权威文档、产出分支/MR 链接，按审查清单输出结论（问题分级：阻断/建议/确认点）。
- 主会话裁决：哪些问题需要修（修在任务分支上），哪些进联调确认点；裁决通过后交由人工合入。

审查清单（通用维度）：

- 口径一致性：新计算是否复用既有函数/算法，"另写一套"（类型转换、不同算法）是危险信号；
- 重算回写链路：逐行字段按各行自己的日期/序列计算，不能以计算日值覆盖历史行；
- 权威文档对齐：请求/响应字段、枚举、必填项逐项核对；
- 边界：空值/无数据、幂等与并发、软删过滤；
- 关联可行性：外键/join 形态在本地 mock 环境用真实形状的种子数据实测；
- 外部依赖隔离：测试是否纯本地通过（不连任何外部/共享环境）、外部依赖是否全部 mock、测试配置是否混入真实凭据/地址——发现真实环境引用即为阻断；
- 生成器注册完整性：新增包/资源必须出现在生成器的聚合与注册文件（如 blank import 列表、service 注册入口）中，这类"应改未改"的缺失不在 diff 里，静态检查（编译/lint）无法发现；
- 运行时冒烟：编译通过 ≠ 服务可运行；注册、中间件、路由绑定等都是运行时行为，验收须以本地 mock 配置真实启动服务并实际调用一次新接口（无新接口的任务改为执行一次任务逻辑并验证结果；外部依赖全部 mock，不连共享环境）；
- 风格规范：分层、中文注释、错误处理、标签精简。

### 6. MR 管理

- 合入顺序（由人工执行）：先行件 MR 需先合入迭代基线；任务 MR 互不依赖、可任意顺序合入。
- 每个任务 MR 创建后验证：ahead = 任务自身提交数、behind = 0、diff 不含先行件内容。
- **Agent 不合并任何 MR**：创建、验证、审查、裁决均可由 Agent 完成，合并一律由人工执行。
